      <pre><code>5. Blind SSRF
│
├── Định nghĩa (Definition)
│   ├── Server gửi request
│   │   └── Server thực hiện request tới URL do attacker chỉ định
│   └── Không trả response (No response returned)
│       ├── Attacker KHÔNG thấy được kết quả trả về (không có HTML, không có lỗi, không có data)
│       ├── Khác với SSRF thông thường (In-band) - nơi response được hiển thị lại cho attacker
│       └── Khó khai thác hơn vì không biết bên trong xảy ra chuyện gì
│
├── Phát hiện (Detection)
│   │   Mục đích: Xác nhận SSRF tồn tại dù không thấy response
│   │
│   ├── Burp Collaborator
│   │   ├── Tạo domain/subdomain độc nhất do Burp kiểm soát

## 📖 Nội dung chi tiết bài viết (Writeup)

<div id="doc-67c6bc7897dacbd26c645c8d062c638ac66457e9" class="notion-callout-card">

```
5. Blind SSRF
│
├── Định nghĩa (Definition)
│   ├── Server gửi request
│   │   └── Server thực hiện request tới URL do attacker chỉ định
│   └── Không trả response (No response returned)
│       ├── Attacker KHÔNG thấy được kết quả trả về (không có HTML, không có lỗi, không có data)
│       ├── Khác với SSRF thông thường (In-band) - nơi response được hiển thị lại cho attacker
│       └── Khó khai thác hơn vì không biết bên trong xảy ra chuyện gì
│
├── Phát hiện (Detection)
│   │   Mục đích: Xác nhận SSRF tồn tại dù không thấy response
│   │
│   ├── Burp Collaborator
│   │   ├── Tạo domain/subdomain độc nhất do Burp kiểm soát
│   │   ├── Nhét domain đó vào payload SSRF
│   │   ├── Nếu server gọi ra ngoài -> Burp Collaborator nhận được request
│   │   └── Xác nhận SSRF thành công
│   │
│   ├── DNS callback
│   │   ├── Attacker dùng domain do mình kiểm soát (ví dụ: evil.com)
│   │   ├── Server thực hiện request tới subdomain của evil.com
│   │   ├── DNS server của attacker ghi log truy vấn
│   │   └── Nếu có log -> SSRF tồn tại (dù không thấy response)
│   │
│   └── HTTP callback
│       ├── Attacker mở listener trên server của mình
│       ├── Payload SSRF trỏ tới IP/domain của attacker
│       ├── Nếu server kết nối tới -> attacker thấy kết nối trong log
│       └── Cách này yêu cầu outbound HTTP từ victim ra ngoài
│
├── Khai thác (Exploitation)
│   │   Mục đích: Lợi dụng SSRF để làm việc gì đó hữu ích dù không thấy response
│   │
│   ├── Data exfiltration (Trích xuất dữ liệu)
│   │   ├── Dùng SSRF để gửi dữ liệu từ internal system ra ngoài
│   │   ├── Ví dụ: Gửi DNS query chứa dữ liệu tới domain của attacker
│   │   ├── Hoặc: Ghi file nội bộ vào thư mục web public
│   │   └── Kỹ thuật: Time-based (đo thời gian response để suy đoán data)
│   │
│   ├── Internal interaction (Tương tác nội bộ)
│   │   ├── Dùng SSRF gửi request tới internal API/dịch vụ
│   │   ├── Ví dụ: Redis, Elasticsearch, Docker API, Jenkins
│   │   ├── Không cần thấy response, chỉ cần request được thực thi
│   │   └── Ví dụ: Gửi lệnh xóa user qua API nội bộ (dù không thấy kết quả)
│   │
│   └── RCE chain (Chuỗi dẫn đến RCE)
│       ├── Kết hợp Blind SSRF với lỗi khác để có RCE
│       ├── Ví dụ 1: SSRF tới Redis -> Ghi webshell vào web root -> Truy cập webshell
│       ├── Ví dụ 2: SSRF tới Docker API -> Tạo container chạy lệnh
│       ├── Ví dụ 3: SSRF tới Jenkins -> Tạo job chạy script
│       └── Điểm mấu chốt: Blind SSRF thường là bước đệm, không phải đích cuối
│
└── Nâng cao (Advanced)
    ├── Time-based Blind SSRF
    │   ├── Đo thời gian phản hồi của server
    │   ├── Nếu server mất nhiều thời gian -> có thể đang chờ internal service
    │   └── Dùng để quét port, quét service nội bộ
    │
    ├── Gopher protocol
    │   ├── Giao thức mạnh nhất cho Blind SSRF
    │   ├── Cho phép gửi raw TCP stream
    │   ├── Tấn công được Redis, MySQL, FastCGI
    │   └── Kết hợp với SSRF để ghi file, tạo reverse shell
    │
    ├── Bypass filter nâng cao
    │   ├── DNS rebinding (đã học)
    │   ├── URL parser confusion (đã học)
    │   └── Redirect chain (đã học)
    │
    └── Công cụ hỗ trợ
        ├── SSRFmap
        ├── Gopherus
        ├── Burp Collaborator
        └── interactsh
```
